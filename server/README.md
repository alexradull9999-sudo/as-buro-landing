# Отправка заявок через SMTP на Timeweb Cloud

Обработчик готов к подключению, но ещё не включён на основном сайте. Текущее приложение Timeweb — **AC buro**, ID `285817`, тип **HTML/CSS/JS**, ветка `main`. Оно продолжает использовать FormSubmit с исправленными адресами возврата. Само добавление этих файлов не переключает способ отправки.

## Что делает сервер

Один процесс Node.js 24 отдаёт существующий сайт и принимает обе формы. При выдаче `index.html` он меняет только параметры отправки: квиз обращается к `/api/leads/quiz`, короткая форма — к `/api/leads/callback`. В серверной версии нет запросов к FormSubmit. Внешний вид, вопросы, портфолио, стили и PDF остаются прежними.

Письмо отправляется на `offer@a-s-buro.com`. Темы, источник и страницы благодарности выбираются сервером. Поля `_next`, `_subject`, `to` из запроса не могут изменить получателя или перенаправление. Посетитель, его телефон и UTM не могут задавать почтовые заголовки.

Сервер проверяет телефон, мессенджер, согласие и допустимые ответы квиза. Базовая защита от спама: поле-ловушка, подписанный токен формы сроком два часа, проверка источника запроса, ограничение размера и частоты. Действует максимум пять попыток за десять минут на адрес и сто за час на процесс. Это не полноценная CAPTCHA: при целевом спаме потребуется дополнительная защита.

Повторные и одновременные запросы с одним токеном и теми же данными используют одну отправку. При ошибке сервер возвращает понятное сообщение; в браузере остаются введённые данные. Успешный ответ и переход на страницу благодарности происходят только после подтверждения SMTP о приёме письма для адресата. Это подтверждение не доказывает попадание во «Входящие».

Контакты не записываются на диск, в браузерное хранилище или логи. Логи содержат только номер заявки, тип формы и факт приёма/ошибки. SMTP-соединение требует TLS с проверкой сертификата; незашифрованный порт 25 не используется.

## Что нужно перед включением

1. SMTP-сервер, порт 465 или 587, логин и пароль **отдельного служебного отправителя сайта**. Адрес `offer@a-s-buro.com` используется только как получатель (`LEADS_TO`): его пароль, подключение и доступ к содержимому ящика не требуются. `SMTP_USER` и `MAIL_FROM` относятся к отправителю. Перед созданием нового платного отправителя согласуйте его стоимость отдельно от размещения сервера.
2. Серверное размещение на Timeweb: приложение **Dockerfile** или существующий сервер с Node.js 24. Статический режим HTML/CSS/JS не запускает этот обработчик. Новый серверный тариф и стоимость необходимо согласовать с владельцем до заказа.
3. Возможность исходящего SMTP-соединения с выбранного размещения. Уточните ограничения у Timeweb до переноса домена.
4. Рабочая DNS-зона домена получателя `a-s-buro.com`, включая актуальные MX-записи его почтового провайдера. При проверке 10 ноября 2026 года Google DNS и Cloudflare возвращали SERVFAIL; серверы `ns1.timeweb.ru` и `ns3.timeweb.org`, указанные в делегировании, отвечали REFUSED на MX-запрос. В доступном аккаунте Timeweb Cloud домен `.com` отсутствовал. Не восстанавливайте записи по предположению и не меняйте почтового провайдера: правильную зону должен подтвердить администратор домена. Замена FormSubmit сама по себе эту проблему не исправит.

Пароли вводите непосредственно в runtime-переменные Timeweb, а не в HTML, GitHub, Dockerfile или чат. Для локальной работы можно скопировать `.env.example` в `server/.env`: этот файл исключён из Git и Docker-контекста.

Обязательные переменные: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM`. `MAIL_FROM` — один разрешённый провайдером адрес отправителя, обычно совпадает с `SMTP_USER`.

Дополнительные переменные:

- `SITE_ORIGIN=https://a-s-buro.ru` — адрес основного сайта без пути.
- `LEADS_TO=offer@a-s-buro.com` — получатель по умолчанию.
- `PORT=8080` — порт, объявленный в Dockerfile.
- `FORM_SECRET` — случайная строка минимум 32 символа. Без неё секрет меняется после перезапуска, и открытые ранее формы нужно обновить.
- `TRUST_PROXY_HOPS=0` — не доверять заголовкам IP. За проверенным единственным прокси укажите `1`, только если он гарантированно перезаписывает/дополняет `X-Forwarded-For`. Если оставить `0` за общим прокси, лимит пяти попыток будет общим для посетителей. При нескольких прокси сначала проверьте их число и правила заголовков.

## Проверка до переноса домена

Локально, из корня репозитория:

```sh
npm --prefix server ci --ignore-scripts
npm --prefix server test
```

Из директории `server`, после заполнения локального `.env`:

```sh
npm run check:smtp
npm start
```

`check:smtp` проверяет подключение, TLS и авторизацию, **не отправляя письма**. При запуске сервер также проверяет SMTP и не начинает обслуживать сайт при неверной конфигурации. Для локальной отправки задайте `SITE_ORIGIN=http://localhost:8080`. Локальный обычный запуск с реальными реквизитами отправляет реальные письма; автоматические тесты используют подставной отправитель без сетевой отправки.

Для Docker из корня репозитория:

```sh
docker build -t as-buro-landing .
docker run --rm -p 8080:8080 --env-file server/.env as-buro-landing
```

В Timeweb сначала разверните серверную версию на техническом адресе, с одним экземпляром приложения. Выберите этот репозиторий, ветку `main`, тип **Dockerfile**, пустой путь до директории проекта, порт 8080 и путь проверки `/healthz`. Для проверки форм на техническом домене временно задайте его полный HTTPS origin в `SITE_ORIGIN`.

Проверьте квиз и короткую форму: каждое письмо должно реально появиться в ящике с телефоном, мессенджером, согласием, UTM и ответами квиза. Убедитесь в работе PDF, галерей, мобильного меню и в отсутствии запросов к FormSubmit. Проверьте поведение при ошибке SMTP на отдельном тестовом размещении.

Только после этой проверки переключите `a-s-buro.ru` на серверное приложение и задайте `SITE_ORIGIN=https://a-s-buro.ru`. Старое статическое приложение сохраните до завершения проверки домена и HTTPS, чтобы можно было вернуть его привязку при сбое. Не создавайте новый платный сервис и не переносите домен без согласования стоимости и готового SMTP.

## Границы надёжности

Локально пройдены 13 автоматических проверок. В браузере проверены три шага квиза, отправка обеих форм, страницы благодарности, а также сохранение введённых данных при ошибке и успешная повторная попытка. Почтовая отправка в этих проверках имитировалась: реальное SMTP-подключение и получение письма ещё не проверены. Docker-образ в этой среде не собирался — Docker не установлен.

Обработчик синхронно передаёт письмо SMTP-провайдеру; постоянной очереди заявок и базы данных здесь нет. При недоступности почты посетитель видит ошибку и может повторить отправку. Данные не сохраняются как успешно принятая заявка до подтверждения SMTP.

Лимиты и сведения о повторах хранятся в памяти одного процесса. Они сбрасываются при перезапуске и не разделяются между экземплярами. Для масштабирования или гарантированного сохранения заявок при сбоях нужна отдельная постоянная очередь/БД. При обрыве связи после фактического приёма SMTP возможен повтор письма: абсолютной гарантии однократной доставки нет.
